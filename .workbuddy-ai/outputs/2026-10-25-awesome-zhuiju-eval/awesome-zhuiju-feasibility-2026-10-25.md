# 功能可行性评估：三模式聚合（在线影视 / 网盘 / BT）

> **这是上一份报告的修正版口径。** 上一份按「能不能当 BT provider」评，所以在线影视 54 条全判不推荐；
> 按你说的「搜索 → 跳转 / 给链接」口径，**同一个站点可能完全可用**。本报告只回答功能可行性，不写代码。
>
> 实测时间：2026-10-25 17:22–17:35（本机，Chrome UA，15–25s 超时）
> 数据源：`awesome-zhuiju-free` 的 `resources.json`（2026-10-23）+ 本机逐站搜索实测

---

## 0. 直接回答

**能做。** 而且「在线影视搜索 → 跳转」和「网盘搜索 → 给链接」比 BT 更简单：它们不需要磁力、不需要下载器、不需要播放器，只需要**搜索结果 + 一个 URL**。

| 模式 | 结果类型 | 点击行为 | 功能可行性 | 主要卡点 |
|---|---|---|---|---|
| 在线影视 | `{title, detail_url, source}` | 打开系统浏览器 | **可行**，46 家里 8 家已实测可搜 | 一半站点是 SPA/验证码 |
| 网盘搜索 | `{title, pan_type, url, code?}` | 打开链接 / 复制提取码 | **可行但数据源少** | 公开实例要逆向；自建 PanSou 最干净 |
| BT/磁力 | `TorrentResult`（现有） | 复制磁力 / 推送下载器 | **16 家里 7 家可做** | 9 家卡在无资源/认证/纯前端 |

**BT/磁力「功能上做不到」的，按硬度分四类：**

| 类别 | 站点 | 说明 |
|---|---|---|
| **资源本身没有**（绝对做不到） | 爱努努、美剧粉 | 详情页 0 magnet、0 `.torrent`、0 下载链接；一个是播放页，一个只有简介 |
| **不绕过就做不到** | 高清MP4（人机验证）、BD影视聚合（401 认证）、高清族（`forbbiden`） | 不是解析问题，是访问被拒 |
| **要加 headless/逆向才能做** | 找电影时光、磁力狗、SeedHub | 纯前端渲染，没有服务端搜索结果 |
| **站点已死**（不是能力问题） | 磁力帝（502） | 等它恢复即可 |

其余 7 家是「直接能做」或「加一项能力就能做」，见第 4 节。

## 1. 三种模式的数据模型（这是改造的核心，不是 UI）

### 1.1 三种结果类型

```
Torrent  { name, size, seeders, date, magnet, info_hash, detail_url }   // 现有
Video    { title, year?, detail_url, source, poster? }                  // 新增
Pan      { title, pan_type, url, code?, source, date? }                 // 新增
```

- **Video** 不需要播放地址、不需要 m3u8、不需要 WebView。只要 `detail_url`，点击 `openExternal` 打开系统浏览器。
- **Pan** 不需要下载器。只要 `url` + `code`，点击打开链接、复制提取码。
- **Torrent** 完全不动：现有 24 家 provider、聚合层、Torznab、下载器都留在 BT tab。

### 1.2 两种架构方案

| 方案 | 做法 | 影响面 | 评价 |
|---|---|---|---|
| **A（推荐）** | 三个独立 trait / 三个 registry / 三个 tab：`TorrentProvider`（现有）、`VideoProvider`、`PanProvider` | BT 侧零改动；新模块独立 | 符合「核心是库、进程内直调」的现有设计；Torznab 只暴露 BT |
| B | 一个 `Provider` + `enum SearchItem { Torrent, Video, Pan }` | 聚合层、UI、Torznab、状态栏全要改 | 结果混流好看，但用户预期不同，排序/去重也难统一 |

**建议 A。** 理由：三种结果的「下一步动作」完全不同（推送下载器 / 打开网页 / 打开网盘），混在一个列表里只会让 UI 变成三套按钮的条件分支。分 tab 后，每个 tab 的列表、空状态、错误文案都能独立演进。

### 1.3 对现有代码的影响边界（只说边界，不写代码）

- **不动**：`bt-core`、`bt-providers` 的 24 家、`bt-downloaders`、`bt-torznab`、M6 差分门。
- **新增**：`bt-video`（通用 MacCMS 适配器 + 站点配置）、`bt-pan`（PanSou 适配器）。
- **打开外链**：Rust 侧目前 `grep open_external` = **0 命中**，需要加一个 `ShellExecuteW` / `open` crate 的薄封装；Electron 侧已有先例（`electron/main.js:44` 的 `shell.openExternal` + scheme 白名单）。这是 Video/Pan 模式唯一的新平台能力，工作量很小。
- **UI**：顶部加三个 tab；Video/Pan 的行操作只有「打开」和「复制链接」，不显示下载器选择。
- **聚合层**：Video/Pan 各自一个小聚合器即可（并发 + 逐站状态），不需要复用 BT 的 `SearchOutcome`。

## 2. 在线影视：搜索 → 跳转

### 2.1 为什么这个模式最容易

不需要解析播放地址，只需要两样东西：

1. 服务端返回的搜索结果页（HTML 里有标题和详情页链接）；
2. 详情页 URL（点开就能看）。

很多站是 **MacCMS / 苹果CMS**，搜索路径是标准化的：

```
/index.php/vod/search.html?wd=<q>
/vodsearch/-------------.html?wd=<q>
/search/-------------.html?wd=<q>
```

结果链接也集中在 `/voddetail/<id>/`、`/detail/<id>.html`、`/voddetail/<id>.html` 这几种。**一个通用解析器 + 一张站点配置表（base + 搜索路径 + 链接正则）就能覆盖多家**，这是整个三模式里性价比最高的一块。

### 2.3 结论

## 3. 网盘搜索：给出对应链接

### 3.1 四家的真实状态

| 站点 | 实测 | 结论 |
|---|---|---|
| PanSou `pansou.de` | `/search?q=` 是 Next.js 壳（18KB，结果客户端渲染）；`POST /api/search` **404**；只找到 `/api/platforms` | 公开实例要逆向 server action；**上游开源版可自建 API** |
| KK网盘搜 `kkso.net` | Vue SPA；主 bundle 里没有 `/api/` 路径 | 要抓 XHR，成本中等 |
| 追剧吧 `zhuiju.us` | 与 KK 同模板、同 bundle | 同上；内容重叠，做一家就够 |
| 谷哥搜 `gugeso.com` | TLS 握手超时 | 不可用 |

### 3.2 可行路径

**路径 1（推荐）：自建 PanSou**

- 上游 `fish2018/pansou` 是开源项目（14.9k star），自带 API，可 Docker 自建（需自建后实测确认版本）。
- 自建后是标准 `POST /api/search`，返回网盘链接 + 提取码，字段规整。
- 代价：用户要跑一个服务，或者你提供一个托管实例（又回到运维/合规问题）。

**路径 2：逆向公开实例**

- `pansou.de` 的搜索是 Next.js server action，需要读构建产物/抓包，不稳定。
- KK/追剧吧是 Vue SPA，需要抓 XHR；输出是网盘链接。
- 代价：每站一套逆向，站点改版就失效。

### 3.3 数据模型

```
PanItem { title, pan_type: "quark"|"baidu"|"aliyun"|..., url, code?, source, date? }
```

- `pan_type` 决定图标和「打开方式」；
- `code` 是提取码，点击复制；
- 不做转存、不做下载，只做「打开链接 + 复制提取码」。

### 3.4 结论

- **网盘模式技术上可行，但数据源是瓶颈**：公开实例都要逆向，自建 PanSou 最干净。
- 如果不想运维，建议**先不做网盘 tab**，或者只做 PanSou 一家、明确标注「需自建/可能失效」。
- 不要把网盘结果混进 BT 列表：它没有磁力、不能推送下载器，用户预期完全不同。

**统计：A 档 2 家、B 档 5 家、C 档 9 家。**

### 4.2 A 档：直接能做（2 家）

**BD电影首发 `bdflixs.com`**

- `GET /?s=流浪地球` → 结果页，2 个影片页；`/594.html` 有 102 条唯一 magnet，锚文本带片名/规格/体积。
- 需要「搜索 → 详情」两步（`needs_magnet` + `resolve_magnet`），无 seeders。

**POMO `pomo.mom`**

- `GET /?keyword=流浪地球` → 结果卡片；`/199` 56 条、`/198` 29 条唯一 magnet，带体积。
- 有登录插件，部分链接可能要 VIP；4K 原盘体积大。

### 4.3 B 档：能做，但要加一项能力（5 家）

| 站点 | 要加什么 | 成本 |
|---|---|---|
| 磁力熊 | POST 搜索（`classid=1,2`），已有 `bangumimoe` 先例 | 低 |
| ACG.RIP | 网络可达（本机 502，未实测；仓库探活为 200） | 低（等网络） |
| BT世界网 | 下载 `.torrent` + bencode 解析 infohash | 中（核心能力） |
| BT影视 | `/tdown/<id>.html` 二次跳转 + `.torrent` 解析 | 中 |
| 电影港网 | `javascript:void(0)` 按钮背后的 AJAX + `.torrent` 解析 | 中高 |

> `.torrent` 解析是**一次投入、三家复用**的能力：`btsj6` / `btbtla` / `dyg22` 都需要。如果要做，建议一次性加到 `bt-core`，而不是在 provider 里各写一遍。

### 4.4 C 档：功能上做不到（9 家，分四类）

**① 资源本身没有（绝对做不到，2 家）**

- **爱努努 `video.ainunu.com`**：详情页 6KB，0 magnet、0 `.torrent`，是 HLS 播放页。它属于「在线影视」模式，不属于 BT。
- **美剧粉 `mjf2020.com`**：搜索能返回结果（`/ss/?s=老友记` 有 6 个命中），但详情页只有简介，没有 magnet/`.torrent`/下载链接。它可能是「会员/回复可见」模式，当前拿不到资源。

**② 不绕过就做不到（3 家）**

- **高清MP4 `mp4ba.vip`**：搜索页是「人机验证 45 + 46 = 验证」，纯算术验证码。不做绕过就做不到；不建议做。
- **BD影视聚合 `juhebd.com`**：`/search` 返回 `{"code":401,"msg":"请求访问：/search，认证失败"}`。搜索接口要认证，没有凭据就做不到。
- **高清族 `hdzu.org`**：搜索返回 9 字节 `forbbiden`，带 `Referer` 也不行。需要 cookie/反爬策略，当前拿不到。

**③ 要加 headless/逆向才能做（3 家）**

- **找电影时光 `ldysg.win`**：7.5KB 页面，`core.js` 里只有 `location.search` 解析，没有 API；搜索是纯前端。
- **磁力狗 `ciligou.net`**：673B JS shell，SSL 异常；没有服务端内容。
- **SeedHub `sidhub.cc`**：跳 `jw.0uc36bq.com`，页面「加载中...」，纯 SPA。

> 这 3 家如果允许内置 WebView/headless 浏览器，理论上能做；但这与项目「小、快、原生、无 WebView」的目标冲突，**不建议为它们破例**。

**④ 站点已死（1 家）**

- **磁力帝 `cld123.com`**：502。不是能力问题，等它恢复即可。

### 4.5 一句话回答

**真正「功能上做不到」的是 5 家：爱努努、美剧粉（没有资源），高清MP4（验证码），BD影视聚合（401 认证），高清族（反爬）。**
另外 3 家（找电影时光、磁力狗、SeedHub）是「加 headless/逆向才能做」，1 家（磁力帝）是站点死了。其余 7 家都能做。

## 5. 建议的落地顺序（按性价比）

| 顺序 | 做什么 | 为什么 | 预计工作量 |
|---|---|---|---|
| 1 | **在线影视：通用 MacCMS 适配器 + 3 家**（APP影院、独播库、嘀嗒影视） | 不需要磁力/播放器，最快验证「搜索 → 跳转」 | 1 个适配器 + 3 条配置 |
| 2 | **BT：BD电影首发** | 磁力最密，`needs_magnet` 模式现成 | 1 个 provider + fixture |
| 3 | **BT：POMO** | 磁力密度高，补 4K 原盘 | 1 个 provider |
| 4 | **在线影视：再补 5–8 家** | 逐站确认参数，扩大覆盖 | 0.5–1 小时/站 |
| 5 | **网盘：自建 PanSou** | 唯一干净的网盘数据源 | 一个服务 + 一个 adapter |
| 6 | **BT：磁力熊** | 唯一有剧集栏目，但 POST + 限流 | 1 个 provider + 退避 |

**不建议做的三件事**

1. **不要为 3 家纯前端站加 WebView/headless**：违反项目「小、快、原生」的目标，收益只有 3 家。
2. **不要做验证码绕过**：高清MP4 的算术验证码、66 大片网/歪比巴卜的「系统安全验证」都不值得。
3. **不要把三种结果混在一个列表**：BT 行有「推送下载器」，Video 行只有「打开网页」，Pan 行只有「打开/复制提取码」；混在一起会让操作区变成条件分支。

---

## 6. 风险（三模式叠加后）

| 风险 | 变化 | 建议 |
|---|---|---|
| 版权 | 从「BT 索引」扩展到「在线影视 + 网盘」，性质更接近「资源导航」 | 只做搜索/跳转，不缓存、不转存、不内嵌播放 |
| 外链安全 | Video/Pan 都要打开外部站点 | 域名白名单 + 打开前确认；不自动跳转 |
| 稳定性 | 在线影视域名漂移比 BT 站更快 | 每个模式独立 health；失效站点自动降权 |
| 数据质量 | 网盘链接有效期短、提取码易失效 | 标注「可能失效」；不做「永久有效」承诺 |
| 用户预期 | 三种结果不能互相替代 | 三个 tab + 结果类型标签；空状态文案分开写 |

## 7. 复现说明

- 在线影视：对每家首页取 `<form>`（action + text/search input），构造 `?wd=` / `?q=` / `?s=` 候选；再按 MacCMS 的三种标准路径兜底；判定「结果页」的标准是标题含关键词且详情链接 ≥2。
- BT：对每家搜索页取结果链接 → 详情页 → 统计 `magnet:?xt=urn:btih:` 唯一值、`.torrent` 文本、`javascript:void(0)` 按钮。
- 网盘：`POST /api/search`（404）、`/search?q=`（SSR 壳）、`/api/platforms`（存在）。
- 所有请求：Chrome 131 UA、`Accept-Language: zh-CN`、15–25s 超时、每站最多 4 个候选 URL。
